# Product Requirement Document (PRD)

**Project Name:** ClarifySQL — Intelligent Natural Language to SQL with Active Ambiguity Resolution  
**Document Version:** 1.0.0  
**Status:** Ready for Review  
**Target Release:** v1.0.0-MVP  

---

## 1. Purpose

### 1.1 What Problem Does the Product Solve?
Standard Text-to-SQL solutions ("Tutorial AI") perform well on simple, explicit queries (e.g., *"How many users registered in March 2026?"*). However, enterprise production systems fail catastrophically when presented with naturally underspecified, semantic, or ambiguous business questions (e.g., *"Show me last month's best customers"*).

When an ambiguous query is received, naive Text-to-SQL engines make arbitrary internal assumptions (hallucinating specific metrics such as order count, net revenue, or retention frequency) and generate syntactically correct SQL that produces **confidently incorrect business data**. This leads to:
* **Silent Data Corruption:** Business operators make operational and financial decisions based on miscalculated assumptions.
* **Loss of Trust:** Stakeholders abandon self-service data tools after experiencing inaccurate reports.
* **Engineering Overhead:** Data analysts spend significant time triaging why an AI-generated report contradicts official financial metrics.

**ClarifySQL** solves this problem by embedding a **Clarification Engine** between natural language understanding and SQL synthesis. It identifies business, temporal, and schema-level ambiguities before generation, pauses execution to prompt the user with structured, explicit business options, and records verified mappings for reliable query synthesis.

### 1.2 Who Will Use It?
1. **Primary Users (Business Stakeholders & Non-Technical Operators):**
   * Product managers, marketing leads, growth operators, and executives who need accurate, ad-hoc relational database insights without knowing SQL or underlying table joins.
2. **Secondary Users (Data Engineers & Business Intelligence Teams):**
   * Data teams that maintain semantic consistency, audit queries, review ambiguous query logs, and define the standard business metric catalog.
3. **Tertiary Users (Internal Developers & System Integrators):**
   * Application developers embedding conversational analytics into internal dashboards and Slack/Teams bots.

### 1.3 How Does It Align with the Company's Strategic Goals and Initiatives?
* **Democratizing Enterprise Data Access:** Expands self-service analytics coverage from technically fluent teams to 100% of internal staff, reducing dependency on BI team ticket queues.
* **Ensuring 100% Deterministic Decision Integrity:** Replaces probabilistic metric guessing with user-verified query parameterization.
* **Operational Cost Reduction:** Prevents expensive, redundant database compute cycles caused by unoptimized, hallucinatory joins and infinite loops generated by naive models.
* **Bridging the 'Tutorial vs. Production' AI Gap:** Builds defensible internal IP and reusable frameworks for high-stakes enterprise LLM applications using structured outputs and evaluation benchmarks.

## 2. Features

### 2.1 Ambiguity Detection & Classification Engine (ADCE)
#### Requirements:
* **REQ-ADCE-01:** The system must inspect every incoming natural language request against the target database schema (DDL + column comments + foreign keys) prior to query synthesis.
* **REQ-ADCE-02:** The system must classify ambiguity across four distinct dimensions:
  1. *Metric Ambiguity:* Subjective terms (e.g., "best", "top", "active", "churned", "high-value").
  2. *Temporal Ambiguity:* Unanchored or multi-interpretation date references (e.g., "last month" when multiple timestamp columns like `created_at`, `paid_at`, `shipped_at` exist).
  3. *Schema & Entity Ambiguity:* Identical or overlapping terminology across multiple tables (e.g., `orders.amount` vs. `payments.amount`, or user ID vs. customer profile ID).
  4. *Granularity Ambiguity:* Aggregation level not specified (e.g., grouped by individual account, organization, or daily/monthly bucket).
* **REQ-ADCE-03:** The classification must output a strictly validated Pydantic model (`AmbiguityCheckResult`) using structured JSON outputs.

#### Context & Rationale:
Naive LLMs prioritize completing prompts over verifying clarity. By making ambiguity classification a required, isolated stage in the pipeline with its own dedicated prompt and schema, the system prevents speculative SQL generation.

---

### 2.2 Interactive Clarification Dispatcher & Resolution Loop (ICDR)
#### Requirements:
* **REQ-ICDR-01:** If `is_ambiguous` evaluates to `True`, the engine must halt SQL synthesis immediately and generate a human-readable clarification dialogue containing:
  * A clear explanation of what is ambiguous.
  * Between 2 and 4 distinct, mutually exclusive business interpretations.
  * The implied SQL logic/metric definition for each option.
* **REQ-ICDR-02:** The user must be able to select an option via structured identifier (e.g., Option A, B, C) or provide an explicit free-text clarification.
* **REQ-ICDR-03:** The system must update the working context with the user's selected resolution and compile an augmented, unambiguous prompt for the SQL synthesis stage.

#### Context & Rationale:
Users should not be forced to write SQL to fix a query. Providing structured, multiple-choice options minimizes user cognitive load while securing 100% semantic clarity.

---

### 2.3 Deterministic Schema Injection & Semantic Layer
#### Requirements:
* **REQ-SISL-01:** The engine must automatically extract and cache the active PostgreSQL schema, including table definitions, data types, primary/foreign key constraints, and column documentation.
* **REQ-SISL-02:** The engine must support a semantic metadata registry (`metrics.json` or YAML) where engineering teams can declare standard formulas (e.g., `Gross Revenue = SUM(payments.amount) WHERE payments.status = 'completed'`).
* **REQ-SISL-03:** The schema prompt must filter schema injection to only relevant tables using vector similarity or keyword matching to stay within LLM context window limits and reduce noise.

#### Context & Rationale:
Databases rarely have self-explanatory schemas. Exposing foreign key relationships alongside a clean metric dictionary ensures the LLM generates syntactically valid joins and calculates metrics according to certified company standards.

---

### 2.4 SQL Generation, Validation & Read-Only Execution Sandbox
#### Requirements:
* **REQ-SGES-01:** Queries must be generated strictly targeting PostgreSQL dialect standards.
* **REQ-SGES-02:** The system must validate SQL using AST parsing (e.g., `sqlglot`) to guarantee queries are strictly read-only (`SELECT` statements only). Any statement containing `DROP`, `DELETE`, `UPDATE`, `INSERT`, `ALTER`, or `EXEC` must trigger an immediate exception.
* **REQ-SGES-03:** SQL execution must run under a restricted, read-only PostgreSQL role with strict statement timeouts (maximum 10 seconds) and automatic result-set truncation (maximum 500 rows per query).
* **REQ-SGES-04:** If execution fails with a PostgreSQL syntax or runtime error, the engine must trigger an automatic self-correction loop (maximum 2 retries) passing the execution error message back to the LLM.

#### Context & Rationale:
Executing arbitrary AI-generated SQL on production databases presents severe security risks (data loss, SQL injection) and performance risks (runaway unindexed joins). Structural AST validation and sandboxed database roles are mandatory.

---

### 2.5 Parallel Comparative Evaluation Framework ("With vs. Without" Engine)
#### Requirements:
* **REQ-EVAL-01:** The system must maintain an automated evaluation runner that processes an evaluation dataset through two separate pipelines:
  * *Pipeline A (Direct / Baseline):* User Query $\rightarrow$ Direct SQL Generation $\rightarrow$ Execution.
  * *Pipeline B (ClarifySQL):* User Query $\rightarrow$ Ambiguity Check $\rightarrow$ Interactive Clarification $\rightarrow$ Synthesized SQL $\rightarrow$ Execution.
* **REQ-EVAL-02:** The framework must calculate and track:
  * **Execution Accuracy (EX):** Whether the query executed and matched ground-truth data.
  * **Ambiguity Precision/Recall:** Whether ambiguous queries were correctly flagged versus non-ambiguous queries incorrectly blocked.
  * **Semantic Divergence Rate:** The difference in data output between Pipeline A's hallucinated assumption and Pipeline B's clarified execution.

#### Context & Rationale:
Quantifying the difference between "Tutorial AI" and "Production AI" requires side-by-side empirical evidence demonstrating that direct-to-SQL leads to silent data divergence on ambiguous inputs.

## 3. Release Criteria

### 3.1 Functionality (Minimum Functionality for MVP Release)
* [ ] Full support for the core eCommerce schema: `customers`, `orders`, `order_items`, `products`, `payments`.
* [ ] Robust ambiguity detection for metric, temporal, and join ambiguity using Pydantic structured output validation.
* [ ] Interactive CLI and programmatic Python API allowing selection between generated clarification options.
* [ ] Hard AST-level guardrails preventing any non-`SELECT` statement from executing.
* [ ] Baseline vs. ClarifySQL comparative evaluation script calculating execution accuracy across a 30-query verified benchmark.

### 3.2 Usability
* [ ] **Clarity of Options:** Clarification questions and options must be phrased in plain business English (zero raw database column names or SQL syntax in the user-facing prompt).
* [ ] **Minimal Friction:** Completely unambiguous queries must execute directly without asking unnecessary clarification questions (Zero False-Positive interruptions for clean queries).
* [ ] **Clean Result Presentation:** Tabular query outputs rendered cleanly in terminal/UI with human-readable summary explanations.

### 3.3 Reliability
* [ ] **Structured Output Compliance:** $\ge 99.5\%$ of LLM responses must strictly parse into the defined Pydantic schema without validation errors (enforced via native structured outputs or JSON schema modes).
* [ ] **Execution Safety:** 100% containment of unsafe operations; 0 mutating operations allowed past AST validation.
* [ ] **Ambiguity Recall:** $\ge 90\%$ of deliberately ambiguous benchmark queries must be intercepted before direct SQL execution.
* [ ] **False Interception Rate:** $\le 5\%$ of explicit, unambiguous queries may be flagged as ambiguous.

### 3.4 Performance Benchmarks
* [ ] **End-to-End Unambiguous Latency:** Direct query generation and execution completed in $< 2.5\text{ seconds}$ (using high-speed inference providers such as Groq or Gemini 2.5/3 Flash).
* [ ] **Clarification Generation Latency:** Ambiguity classification and multiple-choice synthesis rendered to user in $< 1.8\text{ seconds}$.
* [ ] **Database Execution Timeout:** Hard cap of $10.0\text{ seconds}$ enforced on the database session level for all generated queries.

### 3.5 Supportability & Observability
* [ ] **Structured Audit Logging:** Every transaction logged with a unique trace ID capturing: raw natural language query, ambiguity classification result, user clarification selection, final generated SQL, execution duration, and row count.
* [ ] **Semantic Configuration as Code:** Metrics catalog and table synonyms stored in an easily editable YAML/JSON file, allowing data analysts to update metric definitions without touching application code.
* [ ] **Error Diagnostics:** PostgreSQL error traces intercepted, sanitized (no credential leakage), and logged with full context for model tuning.

## 4. Technical Stack & Architecture

| Component | Technology / Library | Purpose |
| :--- | :--- | :--- |
| **Language** | Python 3.11+ | Core engine implementation |
| **Relational Database** | PostgreSQL 15+ | Target database containing transactional tables |
| **Schema & Validation** | Pydantic v2 | Strict JSON schema enforcement for LLM responses |
| **SQL Parser / Guardrail**| `sqlglot` | AST parsing, dialect validation, read-only enforcement |
| **LLM Provider** | Gemini API / Groq (Llama 3.3 70B) / Ollama | Free or low-cost high-performance structured inference |
| **DB Driver** | `psycopg2-binary` or `asyncpg` | Secure, parameterized database connection management |
| **Evaluation Suite** | `pytest` + custom comparative runner | Benchmark metrics and execution comparison |
